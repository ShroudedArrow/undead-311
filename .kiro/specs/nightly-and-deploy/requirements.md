# Requirements: nightly-and-deploy

## Introduction
Automation and hosting: pull-request checks (CI as the independent judge, testing.md), a nightly deep property-test run, the nightly data refresh in the separate `undead-311-data` repo, static hosting with per-PR deploy previews, caching, failure alerts, a frozen judging-snapshot fallback, a Codespaces dev container, and `make capture` for demo media. After the Dec 4 deadline the judged repo's code doesn't change (tech.md). Only data refreshes, and the site is always served from one origin.

IDs use the prefix `REQ-OPS-`. Layers follow docs/PROJECT.md: **demo-critical** (by Nov 17), **credibility** (by Nov 22), **delight**. Acceptance criteria are in EARS form.

---

### REQ-OPS-CI: Pull-request checks
**Layer:** demo-critical (tests, golden, schemas, lint); credibility (copy-lint, axe, bundle budget, channel post)
**User story:** As the owner, I want every PR checked by CI, so agents never grade their own work.
1. WHEN a pull request is opened or updated, `.github/workflows/ci.yml` SHALL run `make setup`, `make test` (including the test-town golden check), schema validation of the committed fixtures, `ruff check` and the TypeScript compile.
2. THE CI SHALL also run `make copy-lint`, an axe scan of judge mode (no serious or critical violations), a bundle-size budget (first view under 3 MB transferred), `pip-audit` and `npm audit --audit-level=high` (tech.md).
3. WHEN CI finishes, THE CI SHALL post a one-line result to the agent channel with a secret limited to `undead-311-ops` issues. A failure to post SHALL never fail the build.
4. THE CI SHALL pin every action to a tagged version and set least-privilege `permissions:` per job.

### REQ-OPS-PBT: Nightly deep property tests
**Layer:** credibility
**User story:** As the owner, I want rare failures found every night, so a bug the fast profile misses doesn't reach judging.
1. `.github/workflows/deep-pbt.yml` SHALL run nightly with the Hypothesis `deep` profile (10× examples) and a saved example database cached between runs. It SHALL also run the fast-check properties with 10× runs.
2. WHEN it finds a failure, THE job SHALL open (or update) a `type:finding` issue labeled `to:engine` or `to:web` in the channel, with the shrunk example.

### REQ-OPS-HOST: Static hosting and previews
**Layer:** demo-critical
**User story:** As a judge, I want a working URL with no login, so I can try the site; as the owner, I want a preview per PR, so I can review changes visually.
1. THE site SHALL be deployed as static files from `web/dist` to the chosen static host (Netlify, the owner's decision of 2026-11-13), with the production URL recorded in the README.
2. WHEN a pull request is opened, THE host SHALL publish a deploy preview and post its URL on the PR.
3. THE deploy SHALL set the CSP and cache headers from files generated by the web build (`_headers`, or the host's equivalent).
4. THE hosting setup SHALL need no paid plan and no secret in the repo. Account linking is a human step, documented click by click in `docs/DEPLOY.md`.

### REQ-OPS-CACHE: Caching
**Layer:** credibility
**User story:** As a phone user, I want repeat visits to load instantly while data stays fresh, so the site feels fast and never shows stale numbers.
1. Hashed asset files SHALL be served with `Cache-Control: public, max-age=31536000, immutable`. `index.html`, `status.json` and data manifests SHALL be served with `no-cache`. Data files SHALL be plain JSON; the host compresses responses, and no precompressed `.gz` files are shipped (ops#184).

### REQ-OPS-PUBLISH: Exports as a release asset
**Layer:** credibility
**User story:** As the owner, I want each full-data run's exports to reach the live site without running the pipeline on a GitHub runner.
1. `pipeline/scripts/exports_release.py publish` SHALL pack a run's export folder into `exports-<run-id>.tar.gz` (with a `MANIFEST.json`, status last) and a SHA-256 file and attach both to the release `exports-<run-id>` of `ShroudedArrow/undead-311-data`. It SHALL refuse an export whose status is not `ok: true` or that carries a `DRY RUN ONLY` anomaly. It SHALL read its token from `DATA_RELEASE_TOKEN` (never `GH_TOKEN`) and use only the GitHub REST API (no `gh`, no GraphQL): create or find the release, upload each asset to the uploads endpoint, download it again with the token and compare its SHA-256 and size with the local file. A mismatch, a short body or an HTTP error SHALL stop the command with exit code 1 and no success message; the token SHALL go only to the API and uploads hosts (never to the signed storage redirect) and only over https (or loopback in tests).
2. `unpack` SHALL verify the hash, reject unsafe paths, accept only files the pipeline owns, and never touch `frozen/`.
3. The nightly job in the data repo SHALL download the newest `exports-*` release with its own token, unpack it, build the site and deploy it to Netlify; it SHALL NOT run the pipeline.

### REQ-OPS-NIGHTLY: Nightly data refresh (separate repo)
**Layer:** credibility
**User story:** As a reader after the deadline, I want fresh data without code changes, so the site stays current until Jan 29, 2027.
1. THE judged repo SHALL contain `ops/undead-311-data/.github/workflows/nightly.yml` and its README as a template. A person copies it into the `undead-311-data` repo (agents have no access there).
2. THE nightly job SHALL check out the judged repo at the frozen release tag, run `make data-download` and `make pipeline`, build the site with the new data, and deploy the whole site to the same host. Data is therefore always served from the site's own origin. This deliberately extends tech.md ("publishes data files the static site loads"): loading data from another origin would break the same-origin CSP and the no-third-party-requests rule.  Hosting is Netlify (owner decision, 2026-11-13).
3. IF any stage fails, THEN THE job SHALL keep the last good deploy, write a failed `status.json` entry into the next successful deploy's history, and alert the team (REQ-OPS-ALERT).
4. THE job SHALL attach the processed Parquet snapshot to a GitHub Release in `undead-311-data`, so new sandboxes download one file instead of rebuilding.

### REQ-OPS-ALERT: Failure alerts
**Layer:** credibility
**User story:** As the owner, I want to hear about a failed night, so the site never quietly goes stale.
1. WHEN a nightly, CI-on-main or deep-PBT job fails, THE job SHALL open a `needs-human` issue in the channel. It SHALL rely on GitHub's own failure email as the fallback.

### REQ-OPS-SNAP: Frozen judging snapshot
**Layer:** credibility
**User story:** As a judge, I want the numbers in the video and on the site to match, so the demo is reproducible.
1. `make snapshot` SHALL freeze the data through a fixed date: it writes the processed files and their SHA-256 hashes to `data/SNAPSHOT.md` (judging section) and tags the release.
2. Judge mode and the video SHALL use the frozen snapshot. IF the nightly refresh fails or is disabled, THEN the site SHALL keep serving the frozen snapshot.
3. THE judging section SHALL hash what a run leaves behind, not a file type the pipeline never writes: the raw input files (`raw/<name>`), the row count of every DuckDB table (one hashed pseudo-file plus a table in the section; the DuckDB file's own bytes differ between identical builds), `run_report.json`, and every file under `web/public/data` except `frozen/`. The pipeline writes no Parquet (docs/DECISIONS.md, 2026-11-16).
3. `make snapshot RUN_ID=<run>` SHALL read the run's own export folder (`$DATA_DIR/exports/<run>`), never `web/public/data`, refuse a failed, dry-run, non-full or foreign-processed run, record the run id, data version and stage (provisional or final) in the judging section, and copy the judge-mode files (tour, points, the tour zombies' card shards) into `data/judging/`. The table is the manifest of every file; `data/judging/` is the only data the tag carries. `make snapshot-verify` SHALL re-check a tag from a plain checkout without any data: the combined hash follows from the table rows, and `data/judging/` holds exactly the judge-mode files with matching hashes. The nightly job freezes judge mode from `data/judging/`.
4. `make judging-final RUN_ID=<run>` SHALL, once `data/labels/validation_labels.csv` has a zombie labeled by two raters and at least three confirmed zombies, regenerate only `stats/validation.json`, `stats/judge_tour.json`, the field-validation block of `docs/VALIDATION.md` and `data/judging/`, and amend the judging section (stage final, tag `judged-<date>-final`). It SHALL change nothing and exit non-zero while labels are missing or fewer than three zombies are confirmed, and SHALL refuse (restoring the two files) when any other export file differs from its hash row. While validation says `awaiting_field_labels` the provisional tour SHALL play with its notice; only `make build JUDGING=1` refuses it.

### REQ-OPS-DUCK: DuckDB connection settings
**Layer:** credibility
**User story:** As the owner of a full-data run, I want DuckDB to leave room for the Python stages and to spill under `$DATA_DIR`, so a run on 3 million rows neither runs out of memory nor loses its temp files.
1. EVERY DuckDB connection the pipeline opens (ingest, export, sample builders, fixtures, in-memory ones included) SHALL go through `undead311.duck` and get: `memory_limit` 65% of RAM (the cgroup limit when lower), `threads` equal to the CPUs the process may use, `temp_directory` `$DATA_DIR/tmp` (tech.md fallback), and `max_temp_directory_size` 20 GB.
2. An environment variable (`UNDEAD311_DUCKDB_MEMORY_LIMIT`, `_THREADS`, `_TEMP_DIR`, `_MAX_TEMP`) SHALL override the matching default.
3. A test SHALL fail when pipeline code calls `duckdb.connect` directly.

### REQ-OPS-RUN: Resumable full run
**Layer:** credibility
**User story:** As the owner, I want a long run that survives an agent restart and tells me where it is, so one interruption does not cost an hour.
1. EACH pipeline stage SHALL be timed and its peak resident memory sampled; the stage table (seconds, peak MB, rows) SHALL be in `run_report.json` and in the run log.
2. WHEN `stages_dir` is given, THE pipeline SHALL commit each database stage and its done-marker in one transaction, and a restart with the same inputs (snapshot text, parameters, raw file sizes) SHALL skip the finished stages and return their stored report fields. Changed inputs SHALL start fresh.
3. EACH finished stage SHALL also be written as `<stages_dir>/NN-<stage>.done.json`.
4. `pipeline/scripts/run_full.py` SHALL post one comment per finished stage to the run-log issue (a comment that cannot be posted is queued, never fatal), stop the run for good when one stage fails twice (leaving the database, markers and logs in place), and stop when the kill-switch file exists.
5. AFTER a run it SHALL write the Coroner coverage on closed in-scope cases and the 300 most common unlabeled closure templates (by case count) to `$DATA_DIR/reports/<run-id>/`.
6. `run_full.py` SHALL write `<run-id>.done.json` after every leg (`--done-file`; default `.kiro/workflow-runs/<run-id>/<run-id>.done.json`) with `done: true` only when the pipeline finished. `.kiro/workflows/fulldata.workflow.yaml` runs one leg per loop iteration (`--budget-min 18`) until that file says `done: true`.
7. WHEN the done file of the run already says `done: true`, `run_full.py` SHALL exit 0 at once: no stage runs, and the done file, markers, logs, database, exports and reports are neither rewritten nor deleted.
8. WHEN a leg ended after the database rename but before the done file was written, the next leg SHALL NOT treat the missing partial database as a fresh start. The pipeline writes `complete.json` (the inputs' fingerprint) and `run_report.json` before the rename; with `reuse_complete` and the same fingerprint it returns the stored report, and `run_full.py` then writes the Coroner coverage and the done file and removes `complete.json`. Changed inputs SHALL still start fresh.

### REQ-OPS-DEV: Codespaces dev container
**Layer:** credibility
**User story:** As a judge or contributor, I want to run the project in the browser with nothing installed, so trying it takes minutes.
1. `.devcontainer/devcontainer.json` SHALL let anyone open the repo in GitHub Codespaces and run `make setup && make pipeline-sample && make web` with nothing installed (Python 3.11, uv, Node from `.nvmrc`, pinned versions).
2. THE dev container SHALL set `DATA_DIR` to the gitignored `.local-data/data` and forward the dev-server port.

### REQ-OPS-CAPTURE: Demo media
**Layer:** delight
**User story:** As the owner, I want gallery screenshots, the time-lapse and clean footage from one command, so the video and Devpost page match the real site.
1. `make capture` SHALL use Playwright to record the judge-mode tour as video, screenshot every page at desktop and phone sizes, and render the time-lapse as a GIF into `docs/media/`, from the frozen snapshot.
2. THE capture SHALL blur or exclude any third-party logo or city mark.

### REQ-OPS-EVID: Evidence commands
**Layer:** delight
**User story:** As a judge, I want to see how the agents built the project, so the Kiro write-up is backed by data.
1. `make channel-export`, `make trace` and `make kiro-stats` (structure.md) SHALL produce `docs/AGENT_CHANNEL.md`, `docs/TRACEABILITY.md` and per-agent and per-run counts from commit trailers. `make channel-export` SHALL use a read-only token supplied at run time and SHALL never write secrets into the output.
