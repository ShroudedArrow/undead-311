# Methods

This page is written by the engine for the parts it implements. The statistical sections (baseline, survival, fair comparisons) are owned by durability-stats and follow `.kiro/steering/methods.md`. Definitions come only from `.kiro/steering/zombie-definition.md`.

## Confidence score

**Status: pending owner approval.** The weights below are a proposal. The owner must approve them before the first full-data run (REQ-CONF.1). The score is computed in `pipeline/undead311/detect/confidence.py`.

```
confidence = clamp01(0.20*match + 0.15*gap + 0.10*specificity + 0.15*label + 0.30*baseline + 0.10*skeptic)
```

Each term is in [0, 1]:

| Term | Weight | Definition |
|---|---|---|
| match | 0.20 | segment: `1 - d / (2 * MAX_SEGMENT_DIST)`. intersection: `0.9 * (1 - d / (2 * INTERSECTION_M))`, where `d` is the sum of the two distances to the intersection. radius: `0.8 * (1 - d / RADIUS_M)`. Closer is higher; segment beats intersection beats radius. |
| gap | 0.15 | `1 - gap_days / WINDOW_DAYS` (a shorter gap is higher). |
| specificity | 0.10 | 1 for a specific type; 0.7 for a catch-all type that inherited its family from a legacy case. |
| label | 0.15 | Coroner label of the original: resolved 1.0, made_safe_temporary 0.9, noted 0.8, referred 0.7, planned_followup 0.6, other 0.6, bulk_backlog 0.5. If the incident has `bulk_closure`, the term is `min(label, 0.5)`. `invalid` and `duplicate` never reach scoring (they are separate deaths). |
| baseline | 0.30 | `1 - baseline_p`, the local chance of coincidence (lower chance of coincidence gives higher confidence). **Neutral 0.5** only for a zombie whose incident has no baseline estimate. |
| skeptic | 0.10 | The surviving Skeptic objections: survives 1.0, weakened 0.5, explained_away 0.0. **Neutral 0.5** while the verdict is `not_reviewed` (a `weakened` verdict also scores 0.5 but is not neutral). |

`confidence_partial` is `true` exactly when a neutral term was used (no `baseline_p`, or Skeptic `not_reviewed`). The score is never used to choose judge-mode zombies or the validation sample; raters are blind to it.

**Where the two evidence terms come from.** `baseline_p` comes from the stats stage: `undead311.stats.pipeline.zombie_baselines(con, result, cases, params)` returns `{zombie_id: baseline_p}` (REQ-STAT-BASE.4), each value a number in [0, 1]. The engine stores it on the zombie and rescores; a value outside [0, 1] fails the run instead of being clamped, and a zombie missing from the mapping keeps the neutral 0.5 and is reported as an anomaly. The same value goes into `skeptic_input.json` as evidence for the Skeptic. The Skeptic verdict comes from `data/labels/skeptic_objections.json`, joined by (incident ID, resurrection ID). A score is complete (`confidence_partial = false`) when the zombie has both a `baseline_p` and a Skeptic verdict other than `not_reviewed`. The stats stage now provides it for every zombie (the same-spot baseline with its fallbacks, below), so a score is partial only while the Skeptic has not reviewed the zombie; the run report counts both (`baseline_zombies`, `confidence_partial`). `zombie_baselines` is the adapter over `BaselineModel.estimate`; the integration test `test_req_conf_2_integration_the_real_stats_stage_gives_every_zombie_a_baseline_p` runs the real hook.

Weights, the intersection factor (0.9, raised from the 0.7 in design.md so that segment > intersection > radius holds at equal distance) and the radius factor (0.8) are proposals and are not validated against the hand-checked sample yet.

## Mirror pairs (REQ-DET-2.4; zombie-definition step 9)

A cross-system pair (legacy and new) of the same family and location, opened within `MIRROR_WINDOW_HOURS` = 6, is one report filed twice. The earlier-opened copy (ties by case ID) is processed normally: it can be a re-report of another incident and, if closed, an original. The later copy is the mirror: it joins no incident, is never an original and attaches to no incident as a re-report, so the pair counts once in every denominator. A copy of a mirror is not itself the original report (A legacy, B new 1 h later, C legacy 2 h later: only B is a mirror). The run report and `status.json` carry `mirror_copies_merged`. Same-system pairs never use this rule. The partition rule of testing.md #12 (every closed in-scope case is in one incident) therefore holds for closed cases that are not mirror copies; steering still words it without the exception.

## Closed on time vs stayed fixed (demo-critical part)

The scorecard (`stats/scorecard.json`) counts closed cases that belong to an eligible original: not a transfer or a new-system Transitioned closure, and closed at least `WINDOW_DAYS` before the data ends. The on-time rate is on-time cases over cases whose `on_time` flag is known (legacy `on_time` ONTIME or OVERDUE; new-system `on_time`). The raw stayed-fixed rate is on-time cases whose incident has no possible zombie, over the same denominator, so it is never above the on-time rate. Both carry Wilson 95% intervals. Planned follow-ups and separate deaths count as not resurrected. The headline set counts headline zombies only; the "all" set counts every tier. The adjusted rate is described under "Durability statistics" below.

Sample caveat: `data/sample/sample_311.csv` is built to hold many re-report pairs, so its rates (about 70% on time, 49% stayed fixed) show that the scorecard works and are not citywide figures. The raw legacy files name the columns `on_time` and `sla_target_dt`; the pipeline also accepts the older spellings `ontime` and `target_dt`.

## Street segments and intersections (credibility; REQ-ING-SNAP)

**Snapping.** Every in-scope case is snapped to the nearest Boston Street Segments (SAM) line. Distances are measured in a local metre projection (origin 42.33 N; the error over Boston is below 0.2% of a distance). `segment_id` and `segment_snap_m` are stored for the nearest segment within 100 m. A case counts as snapped only when `segment_snap_m` is at most `SEGMENT_SNAP_M` (15 m). Ties between equally near segments go to the smallest segment ID, so a run never depends on row order. Z-level: 986 of the 19,442 segments are not at ground level (`F_ZLEV` or `T_ZLEV` is not 0). A case snaps to the nearest ground segment within `SEGMENT_SNAP_M` when there is one, so a case under a bridge or ramp does not snap to the road above it. If no ground segment is within 15 m, it snaps to the nearest segment of any level. A ground-snapped case records only ground-level intersections. The run report counts the cases whose snap changed because of this rule (`z_preferred_cases`). A case that really sits on an elevated road with a ground street beside it still snaps to the ground street; SAM gives no height for a point, so the two cannot be told apart. Rows that already carry a `segment_id` (the test town) are not snapped again.

**Intersections.** SAM has no node IDs. An intersection is a segment endpoint (the first or last vertex) that two or more distinct segments share, matched at 6 decimal places of latitude and longitude and at the same z-level (`F_ZLEV` for the first vertex, `T_ZLEV` for the last). An endpoint that only one segment uses is a dead end and is not an intersection. In the snapshot of 2026-11-11 the file has 19,442 segments and 11,802 intersections; 14.7% of the distinct endpoints are dead ends. Each snapped case stores the intersections within `INTERSECTION_M` (15 m) as `near_nodes`.

**Limitation.** A shared endpoint is a segment break, and not every break is a cross street: a street can be split mid-block. The intersection rule can therefore also join two cases on consecutive segments of one street when both lie within 15 m of such a break. The 15 m limit keeps this to cases that are close to each other anyway (at most 30 m apart through the node).

**When the segments file is missing.** No case is snapped, matching falls back to the radius rule only, and `status.json` records `segments: missing` with an anomaly line. The committed sample run (`make pipeline-sample`) never snaps: it needs no raw files.

## Neighborhood names (REQ-ING-NBR.1)

The legacy system reports 17 coarse names and the new system 26 finer ones, so the same area could appear under two names. Both systems are now reported under the legacy-style names. When `raw/neighborhood_boundaries.geojson` is present, every case with a valid point is named by point in polygon against the City's 26 areas (the same rule for both systems; a point in the overlap of Fenway and Allston goes to the first name alphabetically), and the polygon name is folded to the reported name: Allston and Brighton to "Allston / Brighton", Mattapan to "Greater Mattapan", Fenway and Longwood to "Fenway / Kenmore / Audubon Circle / Longwood", South Boston and South Boston Waterfront to "South Boston / South Boston Waterfront". The five areas the legacy system never names go to the legacy name that holds the legacy cases inside their polygon (sample counts): North End 276 of 276, Chinatown 70 of 71, Leather District 33 of 33 and West End 50 of 80 to "Downtown / Financial District"; Bay Village 67 of 71 to "Back Bay", and Downtown itself 546 of 567 to "Downtown / Financial District". Harbor Islands, the 26th area, has no legacy name and no legacy case inside its polygon, so it keeps its own name: it is the one reported name outside the 17 legacy names, and a test (`test_neighborhoods.py`) pins the full mapping of the 26 names. Legacy "Boston" (558 sample rows) is the city, not a neighborhood; with the boundaries file those cases get the area their point lies in. A case whose point is in no polygon, or every case when the file is missing (the run report then warns), keeps its own name folded through the same table. A case left with no area carries no neighborhood and stays out of neighborhood rankings. A side effect to know: legacy names such as "Greater Mattapan" covered parts of Dorchester and Roxbury, so some legacy cases now report under the area their point is in. The run report counts the changed rows (`neighborhood_renamed`).

## Bulk closures (credibility; REQ-BULK)

A (department, close date, template) group is a bulk closure when it has at least 50 closed in-scope cases and at least 10 times the department's usual daily count for that template. The usual daily count is the median daily closure count of that department and template over the days that have closures. The close date is the Boston local date; the template is the closure text with timestamps, dates, case IDs and numbers masked (the same key the Coroner labels use); a case with no department is grouped under "(unknown)". The flag is stored in its own `bulk_closure` field on the case, the incident and the zombie. It never replaces the Coroner label, which the planned-follow-up rule reads. It caps the label term of the confidence score at 0.5 and shows on the card. `bulk_closures.json` lists the flagged groups with their counts and ratio.

**Empty closure text (ZD step 10, ops#90).** A case with empty closure text (nothing left after masking, about 12% of closed new-system cases in the sample) is grouped by its closure code instead of its template: the key is `code:<closure_code>` (for example `code:Resolved`, `code:Noted`, `code:Transitioned`), so a department's text-less closures no longer pool under one empty template. A case with text keeps its template whatever its code.

**One limit of the rule as written (ZD step 10).** A template that appears only on bulk days is its own median, so its ratio is 1 and it can never be flagged. A purge that uses a closure text no one used before is therefore invisible to this detector. The owner kept the rule as written (ops#90).

## Sensitivity runs (credibility; REQ-SENS-RUN)

The detector runs at every point of the grid: matching in {segment, radius}, `RADIUS_M` in {15, 30, 50} and `WINDOW_DAYS` in {30, 60, 90}, 18 points, with every other parameter at its default. One more run drops every case of type Street Light Other (the migration catch-all) at the default parameters. The DuckDB file holds two tables: `grid_run_index` (one row per run, with the tier totals, so a run with no zombie still appears) and `grid_runs` (zombie counts by run, tier, type family and department). In `radius` matching, segments and intersections are ignored; in `segment` matching, `RADIUS_M` only affects pairs where a case has no segment. Skeptic and confidence steps are not part of a grid run. `make pipeline --skip-grid` (the CLI flag) leaves the tables out for quick local runs.

## Payload budget (credibility; REQ-EXP-SIZE)

Autopsy cards are sharded by neighborhood and resurrection year (`cards/<neighborhood>-<year>.json`), so a phone loads only the shard it opens. Every exported `.json` file, including the stats files, gets a `.json.gz` copy that decompresses to exactly the same bytes (gzip level 9, no timestamp, so two runs write identical copies). The first view loads `status.json`, `points.json`, `stats/scorecard.json` and `stats/judge_tour.json`. Their total size before compression must stay under 3,000,000 bytes: an export over the budget raises an error before any file is written, so the previous files stay in place. The run report lists the size of every exported file and the first-view total.

## Safe re-runs (credibility; REQ-ING-NIGHTLY)

`make pipeline` builds everything in staging folders beside the real ones (a hidden `.staging-<pid>-<start time>` folder next to the output folder and next to the processed folder) and the DuckDB file under a temporary name. Only when every stage has succeeded does it swap the files in: each file is replaced atomically, `status.json.gz` and then `status.json` go last, and every file the swap replaces or removes is kept so a failure part-way (including a failed DuckDB rename) puts the previous files back exactly. A stage that raises, including the first-view size check, leaves the previous outputs untouched. After a good run, files that the pipeline owns but did not write this time (an old card shard, a stats file it no longer produces) are removed; files it does not own (for example `sensitivity_grid.json`) are never touched. A killed run leaves its staging folder behind; the next run removes any staging folder whose process (pid and start time, both in the folder name) is no longer running, so a reused pid cannot keep one. Where the start time can't be read, a folder older than a day is removed. A test fails if a `.*.staging-*` folder sits in `web/public` or `web/dist`.

## Durability statistics (credibility; REQ-STAT)

All of these are computed on the headline tier, with the same statistic over all tiers beside it (`tier_set` "all", or an `all_tiers` block); headline values never include `source_unknown`, `city_rereport` or `sensitivity` zombies. Every file carries `data_version`, `dataset` ("sample" figures are not citywide figures), `params` and `seed`. One seed (311) drives every resampling step, so a rerun on the same input is byte-identical. The cohort throughout is the **eligible originals**: incidents with no transferred member, closed at least `WINDOW_DAYS` before the data end. Observed and expected counts always cover the same originals.

**Same-spot baseline (`stats/baseline.py`, REQ-STAT-BASE).** A spot is the matching segment, or a 60 m cell for a case that did not snap. A spot is watched from its first same-family report to the data end. The `WINDOW_DAYS` after every same-family closure there are dead, including the closure of a case that was itself a re-report: a report in them is a possible resurrection (or the next link of a chain), so it is not counted as a chance report and the time is not counted as watched time (ops#113: when a re-report's own closure started no stretch, the next link counted as a chance report and the expected count ran 50% above the true chance on a town with causal re-reports, and 18-20% above it now). What remains is the spot's live time and its live reports. For an incident, `K_s` is the number of other live reports of the spot in season `s` (the spot's first report, mirror copies and the incident's own member reports are not counted; an incident that was itself born in a dead stretch leaves out the live report that started the stretch), `T_s` the live days of `s`, and `d_s` the days of the incident's own window (`WINDOW_DAYS` from its closure) that fall in `s`. The baseline is `p_spot = 1 - prod_s (1 - d_s / T_s)^K_s`: each other report of season `s` lands in the window's `s` days with probability `d_s / T_s`, so this is the Poisson chance that the window holds a report, estimated without bias. This is the estimator for **sparse spots**: fewer than one report per two windows (`DENSE_WINDOWS` × `WINDOW_DAYS` = 120 days) over the watched span, counting every report after the first. A 60-day window that starts late in a season is therefore scored at each season's own rate, not entirely at the rate of the closure's season (ops#111: late-winter closures took the busy winter rate for a window that was mostly spring, and the baseline ran 12 to 18% high on a null town with winter reports at 4x). A season with no live time uses the spot's all-season counts and days for its share of the window. Days are whole 24-hour blocks counted from the first report, in the season each starts in, the same way live days are counted. The first version took the share of comparable windows that held a report; a hit makes the next window unusable, so that share ran 40% too high at sparse spots (mean `p_spot` 0.21 against an observed rate of 0.14 on a null town with a report every 400 days, ops#107). **Dense spots** (at least one report per two windows, owner decision ops#130 and ops#131) use a direct count instead. `p_spot` is the share of sliding `WINDOW_DAYS` windows that start on a whole day of the incident's season, outside the dead stretches after closures, and hold at least one report. Every non-mirror report counts, reports in a dead stretch too, and the incident's own members are not removed. Counting directly drops the Poisson formula, which ran low at spots reported on a near-regular schedule (a report every 30 days) and gave a null town with no resurrections by cause a positive excess whose interval lay above 0. It does not drop every assumption: the windows it counts start on live days, which come after a quiet stretch of at least `WINDOW_DAYS` that follows a closure, so the share is unbiased only for random (Poisson) arrivals. For arrivals on a fixed schedule the live-start windows are biased: at a spot reported every 70 +- 5 days no report ever falls within 60 days of a closure (observed 0, the true chance is 0), yet 78% of live-start windows hold a report, so the expected count is 4,378 on 5,622 originals; the error is on the cautious side. The same bias runs the other way for arrivals that come in bursts (see Limits). Counting the reports in dead stretches can only raise a dense spot's `p` when a real resurrection is there, which is a second reason the excess tends to run below 0 at dense spots. The class depends only on the reports and the watched span, never on closures, so the placebo shift cannot change it. A spot with fewer than 4 windows of the season in its watched span (decided by the first report only, never by what was reported) is read in one of three ways, in this order (ops#136). (1) A **dense spot with a report per window** (the dense class above, and also at least one report per `WINDOW_DAYS`, counting the first report, over the watched span) uses its own sliding-window share however short the spot: the estimate has source `spot`. Without this, a near-regular spot whose first report comes late in the data had every report in a dead stretch, so its live rate and the pooled rate were about 0 and a null town of such spots gave +1,978 to +3,259 with an interval above 0 (ops#131, ops#136). The stricter test for short spots is deliberate: with fewer reports a dense spot cannot be told from a lucky sparse one, and taking every such spot as dense raised the baseline of sparse towns (observed 143, expected 196 on a town of 120 spots with a report every 200 days, and a placebo that warned). (2) Otherwise the fallback is the higher of the neighborhood estimate (when the neighborhood has an area) and the pooled p of the family and season (at least 100 windows, else all seasons). The neighborhood rate is the chance at a random point, and a spot that has reports is busier than a random point, so used alone it ran low and gave +48 to +84 with an interval above 0 on a sparse town with staggered first reports (ops#136). The pooled p of a family is one rate, the live reports over the live days of all its watched spots (the dead stretches are left out of both, as above), turned into the chance that a window holds a report from the days the window has in each season; the pooled p of a season is the mean of this over its incidents. Adding up over all spots gives the pooled rate enough live time, which a spot that falls back cannot give alone (a mean of per-spot p over short-watched spots came out 30% high). One rate treats the spots of a family alike, so it runs low for busy spots when spots differ widely; only the spots watched for less than 4 windows use it. The numbers of originals per source are exported (`baseline_sources` in `excess.json`). `baseline_p` per zombie is that value. Expected = the sum of `p` over the originals, excess = observed headline zombies minus expected, by department, family and neighborhood, with a 1,000-replicate bootstrap interval. Each replicate resamples whole spots (the originals of a spot share the reports behind both their outcome and their `p`) and draws every pooled fallback `p` again as Binomial(n, `p`) / n over its n windows (originals that share a pooled fallback share the draw), a draw that is centred on `p` and stays in [0, 1] without clipping, so the interval always holds its own point estimate when every `p` is 0 or 1 (ops#108). On null towns (300 spots with a report every 100 to 400 days and no resurrection by cause) the interval covers 0 in about 90% of towns and the placebo warns in 5% to 10%. With fewer than 10 independent spots (or pooled cells) in a group there are too few distinct resamples, so the interval is never narrower than the Bernoulli noise of the outcomes, `1.96 * sqrt(sum p (1 - p))` around the excess (ops#115: 12 originals at one spot gave 0.99 [0.99, 0.99]), and the placebo never warns on so few spots. A neighborhood-Poisson `p` has no window count and stays fixed. In `radius` matching (the nine radius-mode grid points) a spot is the 2 × `RADIUS_M` cell for every case, snapped or not, because segments are ignored there (ops#104). Limits and null-town results (ops#130, ops#131, ops#132, ops#136, ops#137): a town where no report is caused by a closure should give an excess near 0, and **the excess interval must never lie above 0**. It does not in any town of the first table below, which covers every owner-listed family (sparse random, seasonal, near-regular 30-day, the ops#114 mixed towns) with first reports from day 0 and with them spread over the first 1,300 days. Two kinds of town lie above 0 and are limits of any baseline built from a spot's own reports (last table): reports that come in bursts (each gap 10 or 200 days at random), where the live-start windows sit in the long gaps and the share runs low (about 0.43 against the true 0.5, +450 to +483), and reports on a fixed schedule whose gap is just longer than `WINDOW_DAYS` plus the closing time, so every re-report lands near the end of the window (every 62 +- 1 days, closed in 2 days: +555 to +577; every 75 +- 2 days, closed in 20 days: +2,249 to +2,338). A re-report 10 days after a closure is what a possible zombie looks like, so no baseline can separate it from a cause when the spot's own schedule produces it. In the schedule town the placebo lies above 0 and warns (+770 to +797), the one place the warning is on the positive side. The owner decides whether these towns join the acceptance (ops#138). At dense spots the excess lies **below 0**. A likely reason (not isolated by a separate test): the estimator counts every report in the window after a closure, while the detector gives each re-report to one incident only (the most recent closure), so with a report every 30 to 60 days several closures share one report and the observed count falls below the number of windows that hold a report. The excess is therefore a floor there: real resurrections at such spots are undercounted by the size of the shortfall (about 5 to 10% of originals on a report every 30 to 60 days). At sparse spots (a report every 300 days or less often) the interval covers 0 or lies below it. The first table gives the seeded null towns of the first version (300 spots, all watched from day 0, 1,400 days, every report closed 2 days after it opens, 1,000 and 300 bootstrap replicates for the excess and shift tests, seed 311). The second table adds near-regular towns and towns whose first reports are spread over the first 1,300 days, which `test_stats_hybrid.py` also runs; the first table's claim that no town lies above 0 covered only towns that watch every spot from day 0, where the short-spot fallback is never used (ops#137). "Placebo" is the placebo excess with its interval; it moves closures independently of the reports. It warns (interval excludes 0) only on the negative side in these towns, never above 0, so read a placebo warning together with the sign: a negative placebo with a negative excess means the baseline is cautious, not that the excess is inflated.

**Neighborhood Poisson check (REQ-STAT-NBR).** lambda = same-family reports per m2 per day in the neighborhood and season, leaving out reports within `RADIUS_M` and +-`WINDOW_DAYS` of the case; `expected = lambda * pi * RADIUS_M^2 * WINDOW_DAYS`, `P = 1 - exp(-expected)`. Areas come from the City's boundaries file (the union of the polygons that fold into one reported name, so the overlap of Fenway and Allston is not counted twice); they are stored in the DuckDB table `neighborhood_areas`. It is exported beside the excess as `expected_nbr` and `excess_nbr`. Without the boundaries file the check is skipped and the status says so.

**Shift test and placebo (`stats/shift.py`, REQ-STAT-SHIFT, REQ-STAT-PLACEBO).** All closures of one spot move by one random offset, circularly, inside the spot's observed span (minus one window, so the shifted window stays inside the data); locations stay. The count is eligible headline-scope originals with at least one same-family report within `WINDOW_DAYS` after the (shifted) closure, no attribution or tiers: `observed` is that count without a shift, so it is comparable with the 1,000 shifted counts (mean, 2.5% and 97.5% quantiles). A shifted closure never counts the incident's own member reports, which a closure moved ahead of them would otherwise pick up as chance hits (ops#102). The detector's own headline count is `headline_zombies`. The placebo recomputes the same-spot live time on the shifted closures for the first 10 shifts (the spot's live closures, moved, make the dead stretches, as in the baseline) and compares each shifted hit with the season-integrated `p_spot` of the moved window, the same function the excess uses, so a shift of 0 gives the excess's own expected (ops#111). For dense spots the placebo uses the same sliding-window share on the moved closures, so a shift of 0 gives the excess's own expected (ops#131). The placebo does not apply the ancestor rule for incidents born in a dead stretch (ops#112); that rule applies to sparse spots only, and the open question stays with the owner. Each original's mean (shifted hit minus baseline) is summed, with a seeded bootstrap interval that also carries the error of the baseline (as for the excess). If that interval excludes 0 the status carries a `calibration_warning`. Originals that used a fallback keep their unshifted value. Limitations: on a sample selected for zombies the warning is expected; in very dense spots (a report every 30 to 60 days) the live rate is noisy and the warning fires more often, on the negative side (see the null-town table above). With fewer than 10 independent spots or pooled cells (MIN_CLUSTERS) the warning is never set; the small-spot floor of the interval reads a placebo value by its own variance, `p (1 - p) / runs` (ops#133).

**Adjusted stayed-fixed rate (REQ-STAT-SF.3).** `adj = min(on_time, raw + E / n)`, where `E` is the sum of `p` over the on-time cases of incidents that are zombies in the tier set, capped at the number of those cases. Wilson interval around the fractional rate; always between raw and on-time.

**With and without city-originated re-reports (`stats/city.py`, REQ-STAT-CITY.1, REQ-DET-TIER.3).** A legacy re-report opened by the city (source Employee Generated, City Worker App or Maximo Integration, or an internal or work-order type) that is not a planned follow-up is a possible zombie in the `city_rereport` tier, outside the headline (zombie-definition step 6, ops#29). The detector classifies the first re-report only, so an incident whose first re-report is a resident's keeps its headline zombie even when a city case follows. New-system re-reports are never moved (origin unknown); the count of those is exported. `scorecard.json` carries `headline_all` (headline plus city tier), `headline_without_city` (the headline) and the size of the city tier. The run report and `status.json` carry `city_rereport_count`, `city_rereport_under_1h_count` and an anomaly when the city tier is at least half of headline plus city. `times_risen` counts the city tier; the repeat-offender test does not. No headline number is published until `data/labels/coroner_labels.csv` exists (owner decision, ops#29).

**Survival (`stats/survival.py`, REQ-STAT-KM).** The engine's `detect()` is rerun with `WINDOW_DAYS` replaced by `SURVIVAL_HORIZON_DAYS = 365`; its zombies are the events. This horizon is a statistics parameter that is not in zombie-definition.md (the 90-day share cannot come from a 60-day window); the owner records it. Times are whole days (an event rounds up, a censoring time down), censored at the data end or 365 days. Kaplan-Meier from lifelines, exponential Greenwood intervals, shares at 7, 30 and 90 days (null past the last observed time), and the half-life where the curve first reaches 0.5. Curves: citywide (`all`), `family:<key>` and `department:<code>` with at least 10 originals, for the headline and all tiers. A resurrection of another tier is not an event for the headline curve, in line with the stayed-fixed rate.

**Small-sample correction and funnel (`stats/groups.py`, REQ-STAT-EB, REQ-STAT-FUNNEL).** Group rate = originals that became a zombie over originals. Beta-binomial prior with mean fixed at the citywide rate and concentration kappa, fitted once per kind (department, family, neighborhood; each kind's groups partition the originals) by maximum marginal likelihood, exported as `kappas` (`kappa` is the family value) (method of moments when the likelihood has no interior maximum); posterior mean `(k + mu*kappa)/(n + kappa)`, always between the raw and citywide rate; the interval is its 95% posterior interval. Funnel limits are exact binomial quantiles of Bin(n, mu)/n at 0.025/0.975 and 0.001/0.999, exported for every n up to 500 and then on a 3% ladder to the largest group. A group is `unusual` only outside the 99.8% limits. `raw_lo` and `raw_hi` are the Wilson interval of the raw rate.

**Reporting intensity (REQ-STAT-REP).** In-scope reports opened per km of SAM street, per neighborhood (street length from segment midpoints in the neighborhood polygons) and per neighborhood and family (`intensity` in `groups.json`). A neighborhood row is exported only with this value; without the boundaries and segments files no neighborhood group or neighborhood excess row is written. Measured counts are a floor.

**Temporary fixes, separate deaths, exclusions (REQ-STAT-TEMP).** Of eligible originals labeled `made_safe_temporary`, the share that became a headline zombie tagged `after_temporary_fix` (legacy resident) and, separately, `source_unknown` (new system). Rows by family, department and citywide, with Wilson intervals. `separate_deaths` counts re-reported `invalid` and `duplicate` incidents; `exclusions` merges the cleaning counts with the excluded-pair counts (`pair_mirror`, `pair_transferred_original`, `pair_linked_successor`).

**Sensitivity grid (REQ-STAT-GRID).** `sensitivity_grid.json` joins the engine's grid runs with two numbers observed during each run: headline excess (same-spot baseline at that point's parameters) and the citywide raw stayed-fixed rate. The run without Street Light Other is `without_street_light_other`.

**Field validation (`stats/validation.py`, REQ-STAT-VAL, REQ-STAT-TOUR.2).** `make validation-sample` draws up to 50 headline zombies re-reported in the 60 days before the data end, from the neighborhoods in `data/labels/validation_config.json` (owner input: `{"neighborhoods": [...], "seed": 311, "n": 50}`), with a fixed seed, and writes `data/labels/validation_sample.csv` without the confidence score. The committed config (owner decision, ops#101) names Fenway / Kenmore, Mission Hill, Roxbury and South End, seed 311, n 50; Fenway / Kenmore is written under its reported name "Fenway / Kenmore / Audubon Circle / Longwood", the one the neighborhood rule produces. It is drawn once and never overwritten. `make validate` reads `data/labels/validation_labels.csv` (`zombie_id, rater, label, visited_on`; labels still broken, fixed since, different issue, can't tell). A zombie is confirmed when both raters say still broken; one can't-tell leaves it out of precision. Precision = confirmed over rated, with a Wilson 95% interval; Cohen's kappa over the four labels and over still broken or not (undefined when chance agreement is 1). With three or more confirmed zombies `judge_tour.json` has `provisional: false` and lists confirmed zombies only (the owner's override if all three are confirmed, else the most re-reports). The provisional tour (before confirmation) ranks by re-reports only among resident-reported headline zombies whose re-report opened at least 1 hour after the closure (owner decision, ops#44), so a crew's work log is never featured.
