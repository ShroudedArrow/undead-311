# 03 — Specs (create in the Kiro IDE spec flow; review requirements and design yourself before tasks)

Create five specs, in this order. For each: requirements in EARS form with IDs, a design that lists correctness properties linked to requirements (enable property-based testing), then tasks. Ask Kiro to check the requirements for contradictions and gaps before moving on.

1. **zombie-engine** — ingest (legacy and Oct-2025+ formats → normalized schema, type crosswalk), SAM street-segment snapping, placeholder-coordinate detection, PII scrubbing, incidents, attribution, chains, planned follow-ups, bulk-closure detector, Coroner label join, confidence score, schema-validated exports. Properties: testing.md #1, 2, 4, 5, 9, 11–16.
2. **durability-stats** — baseline + excess, placebo calibration, reporting-intensity context, with/without city-originated re-reports, shift-test robustness, Kaplan-Meier survival, empirical-Bayes shrinkage, funnel plot data, stayed-fixed rates, sensitivity grid, validation precision (Wilson interval). Properties: #3, 6, 7, 8, 10.
3. **haunted-web** — map with filters, "Check my street" search, autopsy cards, repeat-offenders view, two-number scorecard, survival and funnel charts, leaderboards, methods page with sensitivity sliders, data-freshness/status, report-an-error link, judge mode tour, accessible table view, permalinks, share images, reduced motion, design-system.md compliance. Playwright e2e for the judge-mode path. fast-check properties for client-side filtering/aggregation.
4. **undead-mcp** — MCP server exposing: zombies_near(lat, lon, radius), department_durability(name), case_autopsy(id), weekly_summary(since). Read-only over `$DATA_DIR/processed` (and the published data files when running for the Crew App). Then package as a Kiro Power (POWER.md + mcp.json + steering) in its own repo.
5. **nightly-and-deploy** — GitHub Actions: ci.yml (the PR checks in testing.md, results posted to the agent channel), deep-pbt.yml (nightly deep property tests), nightly.yml in `undead-311-data` (download → pipeline → publish data files). Static hosting with deploy previews per PR; caching; failure alerts; frozen snapshot fallback. Plus a `.devcontainer/` config so anyone (including judges) can open the repo in GitHub Codespaces and run `make setup && make pipeline-sample && make web` with nothing installed, and the `make capture` script for gallery screenshots, the time-lapse GIF, and clean demo footage.

Human gate: spend real time on requirements and design. That review is the highest-leverage hour of the project.
